# Activity 2: "Build the Event Loop" — Simulation & Reflection

## Round 3 Questions (Simulating a Blocked Event Loop)

1. **What happened to the other events while you were "stuck" on the slow handler?**
   All remaining events sat waiting in the event queue without being picked up or processed. Because the single event loop was busy executing the 30-second handler, no subsequent events could run until it finished.

2. **What would a user see if this happened in a real application?**
   The user would experience a frozen, unresponsive interface: buttons would not respond to clicks, text fields would not show typed characters, the window could not be moved or resized cleanly, and the OS might display a "Not Responding" message.

3. **How could this problem be fixed?**
   Offload slow or long-running work (such as network requests, database queries, or heavy computations) to a **background worker thread**, keeping the event loop free to process UI events, and then post only the final UI update back onto the Event Dispatch Thread (`SwingUtilities.invokeLater()`).

## Reflection: Event Queue, Event Loop, and Non-Blocking Execution

In an event-driven system, the **event queue** acts as an ordered waiting line (typically FIFO) that buffers incoming event objects generated by user actions, timers, or sensors until the application is ready to process them. The **event loop** continuously monitors this queue, pulls the next waiting event, and dispatches it to the appropriate registered listener and handler. Because a single thread usually drives the GUI event loop (such as Java Swing's Event Dispatch Thread), it can only execute one handler at a time. If a handler performs a slow, blocking task directly on that thread, the entire event loop stalls, preventing repaints, clicks, and keystrokes from being handled and making the application appear frozen to the user. Keeping handlers fast and delegating long-running tasks to background threads ensures the event loop remains responsive at all times.
